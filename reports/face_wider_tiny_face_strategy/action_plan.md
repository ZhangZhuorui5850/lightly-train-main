# 优先级、官方指标来源与行动清单

调研日期：2026-09-10。承接 [report.md](report.md)（根因分析）。本文回答三件事：**指标从哪来、数据到底是不是最次要的、三层操作各该做什么**。

> 数据层面的问题与证据另见 [conversion_audit.md](conversion_audit.md)；当日工作记录与交接起点见 [worklog_2026-09-10.md](worklog_2026-09-10.md)。

---

## 0. 先说结论

**"数据问题最次要"这句话只对一半。** 需要把"数据"拆成两类：

| 类别 | 具体事项 | 优先级 |
|---|---|---|
| 数据 —— **测量基座** | 重建官方 val 评测集、跑官方口径的 easy/medium/hard | **最高**（没有它，你的所有数字都无法对外解释） |
| 数据 —— **划分正确性** | 本地划分是随机切分，导致 test 100% 与 train 共享连拍子场景 | **高**（决定你看到的 mAP 里有多少是记忆） |
| 数据 —— **监督正确性** | 切片边界删掉了可见人脸的标签 | **必修**（正确性问题），但收益上限有限 |
| 数据 —— **增强调参** | 切片比例、Copy-Paste 的目标尺度、混合权重 | **最低**（先别动，等测量修好） |

真正的天花板不在数据，在两个结构性约束：**输入分辨率**（test 有 72.07% 的 GT 小于一个 ViT token）和**输出容量**（300 query + 评测每图 100 框，23.13% 的 GT 永远无法命中）。数据层面能影响的只有约 28% 的可达 GT——这就是为什么"数据增强调参"排在最后。

**建议顺序**：测量基座 → 验证层（SAHI 与分档，零训练成本）→ 分辨率 → 训练方法 → 数据增强。下面逐层展开。

## 1. 指标从哪来：官方 test 确实没有标签

你找得没错。WIDER FACE 三个部分的标签可用性完全不同：

| 部分 | 图片数 | 标签是否公开 | 能拿来做什么 |
|---|---:|---|---|
| 官方 train | 12,880 | 公开 | 训练 |
| 官方 val | 3,226 | **公开** | **可本地复现官方口径评测** |
| 官方 test | 16,097 | **不公开** | 只能提交预测到官方服务器换排行分数 |
| 你们现在的 test | 1,615 | 公开 | 内部 A/B 对比；对外不可比 |

（官方分发包的实际计数是 3,226，与论文里的 3,220 有 6 张出入，这是官方数据的分发计数不一致，本地目录也是 3,226。）

### 1.1 easy / medium / hard 是什么

它们是**官方按检测难度划出的人脸子集**，不是图片子集，也不是我们自己定的尺寸档：

- 定义方式：按 EdgeBox 在每张脸上的检测率，逐步把难样本并进来，得到 easy / medium / hard 三档。
- 实现方式：官方标注包里除了 `wider_face_val.mat`，还提供 `wider_easy_val.mat`、`wider_medium_val.mat`、`wider_hard_val.mat`。每个文件只有一个字段 `gt_list`，给出**每张图里哪些脸属于该难度**（1-based 索引）。
- 评测时：不属于当前难度的脸被记为 ignore——既不算漏检，命中它的预测也不算误检。所以 easy 只考核容易的脸，hard 考核最难的那批。
- 典型量级：Easy 93–96 / Medium 92–95 / Hard 79–86。
- 评测实现：官方 `evaluate.py`，IoU=0.5、VOC 式 AP、1000 个分数档，**没有预测框数量上限**，也不做尺寸过滤（"哪些脸参与考核"完全由难度列表决定）。

**这里要更正我上一份报告里的一句话。** 我在 [report.md](report.md) §1.2 写了"官方属性丢失 → easy/medium/hard 无法重建"，这个说法过重了：难度列表是**独立于属性的 mat 文件**，重新下载官方标注包（十几 MB）就能复现三档指标。丢失的属性影响的是标注约定里的 ignore 标记，而公开的 val 评测代码并不读属性。

顺带把"≤10px 被官方忽略"这个说法讲准：数据集约定会把高度 ≤10px、难以辨认的脸标 ignore；但公开评测脚本里的 ignore 是**由难度列表驱动的**。所以"本地把 ≤10px 当必须检出"这件事，跟官方 easy/medium 比确实是差异，跟官方 hard 比时那些脸本来就参与考核。不要把它当成一个固定的 15% 折扣。

### 1.2 三条拿到"可对外比较"数字的路径

| 路径 | 做法 | 可行性 |
|---|---|---|
| A. 官方 test 排行 | 按官方要求生成结果文件提交给评测服务器 | 唯一能拿到排行数字的路；无法本地自查 |
| B. 官方 val 三档 AP | 下载官方 val 图片 + 官方 `ground_truth/` 包，用官方 `evaluate.py` | **推荐**：本地可复现、可反复跑、可对外引用 |
| C. 自建划分（现状） | 本地 test 1,615 张 + COCO 口径 mAP | 只用于内部 A/B，不能对外引用 |

### 1.3 好消息：官方 val 的图你其实已经有了

我核对了本地语料的文件名前缀——**每一张图都保留了官方来源标记**（0 张例外）：

| 本地 split | `wider_train_` 前缀 | `wider_val_` 前缀 |
|---|---:|---:|
| train | 10,318 | 2,565 |
| val | 1,271 | 325 |
| test | 1,283 | 332 |
| **合计** | **12,872** | **3,222** |

也就是说，**官方 val 的 3,222 张图全部都在本地**，只是被随机切分打散到了三个 split 里（2,565 张混在 train 里！）。所以路线 B 不需要重新下载图片，只需按前缀重组：

1. 用 `wider_val_` 前缀从三个 split 里挑出 3,222 张，组成官方 val 评测集；
2. **把这些图从本地 train 里剔除**——它们现在在训练集里，不剔除就是直接泄漏；
3. 下载官方 `ground_truth/` 包（`wider_face_val.mat` + 三个难度 mat），用官方 `evaluate.py` 跑三档 AP；
4. 得到的第一组三档数字，就是你之后所有改进的对外锚点。

同时，本地 A/B 划分也该修：现在是按图随机切分，导致 61 个事件在三个 split 里 100% 重叠、test 的 1,615 张图全部与 train 共享连拍子场景。**正确做法是按连拍序列（文件名去掉末尾序号后的前缀）分组切分，保证同一序列不跨 split。** 这一步不改变"哪个模型更好"的结论，但让"泛化"这个词有意义。

## 3. 验证层：先做，零训练成本

这一层的意义是：**在花钱重训之前，先把"能不能变好"和"变好多少"测出来。**

### 3.1 分档指标（已就绪）

```bash
python launcher.py eval --task det \
  --data datasets/face_detect/face_yolo_wider/data.yaml --split test \
  --experiment-dir <实验目录> \
  --score-threshold 0.0 --save-json --skip-visualization

conda run -n lightlytrain python reports/face_wider_tiny_face_strategy/band_eval.py \
  --pred-json-dir <实验目录>/eval/<数据集>-<id>/test/_tempfile/json \
  --data datasets/face_detect/face_yolo_wider/data.yaml --split test
```

`--save-json` 是本轮新加的 eval 能力（默认关，也可在 `launcher.py` 里把 `det_eval_save_json` 置 True）。`--score-threshold 0.0` 不能省——JSON 里的预测会被这个阈值过滤。

输出包含：设备像素短边 `<8 / 8–16 / 16–32 / ≥32` 四档，以及 `official_valid`、`official_valid_and_ge1patch`（可达子集）、`dense_images_gt_over_100`、`small_and_dense` 四个子集的 AP50 与召回。参考基线（test 全量）：

| 档 / 子集 | GT 数 |
|---|---:|
| <8px | 9,335 |
| 8–16px | 7,144 |
| 16–32px | 4,088 |
| ≥32px | 2,299 |
| 排除 ≤10px 难以辨认框 | 19,443 |
| 可达（排除 ≤10px 且 ≥16px） | 6,387 |
| 密集图（>100 脸） | 9,090 |

### 3.2 容量诊断

- `maxDets=100` 是 torchmetrics 的默认值，本地 test 有 **5,290 个 GT（23.13%）**落在容量之外。改 `maxDets=300` 重跑一次作诊断，看指标能抬多少——这量化的是"评测设计"而不是"模型能力"。
- 模型自身只输出 300 个 query。test 有 9 张图 GT>300（4,115 个 GT），这些图上召回上限被 query 预算直接锁死。

### 3.3 SAHI 参数：现状、语义与建议扫描

现状（`tool_lib/common.py` 与 `launcher.py` 的 SAHI_SETTINGS）：

| 参数 | 现状值 | 语义 | 建议 |
|---|---|---|---|
| `--sahi` | 关（`det_sahi_enabled: False`） | 是否启用切片推理 | 作为独立对照开启；注意交互式 eval 没有这个提问项，只能改配置键或用命令行 |
| `--sahi-overlap` | `0.2` | 切片步长 =(1−overlap)×切片边长 | 扫 0.2 / 0.3 / 0.4；越大切片越多越慢，但边界脸更少被切断 |
| `--sahi-nms-iou` | `0.3` | 切片之间 NMS 的 IoU 阈值 | 扫 0.2 / 0.3 / 0.5；调低去重更狠 |
| `--sahi-global-local-iou` | `0.1` | 切片框与同类全局框 IoU 超过它就丢弃该切片框 | **调高（0.1→0.3）会保留更多切片框，对小脸有利**，这是最值得先试的一个 |
| `--sahi-skip-small` | 开 | 图比切片小时回退普通 predict | 保持开启 |
| `--score-threshold` | `0.3` | **在合并之前**过滤 | 见下面的口径警告 |
| 切片尺寸 | = 模型 `image_size`，**不放大** | 有效放大中位数仅 **1.18×**，12.8% 的测试图放大倍数正好 1.00× | 需改代码支持 320/448/512，见 3.5 |

**口径警告**：SAHI 路径把 score 阈值在合并前就用掉了，而不开 SAHI 时 mAP 用 `threshold=0.0`。所以"原模型+SAHI"和"combined 全图"这两个数**不是同一打分口径**，只有"两组都开 SAHI"或"两组都不开"的对比才有效。要得到真正同口径的对比，需要把"合并用阈值"与"指标用阈值"解耦（小改：合并用低阈值，指标阶段再过滤），这是一个独立的验证层改动项。

### 3.4 统计显著性

两次实验相差 0.94 个百分点，而这个量级在单 seed 下完全可能是训练噪声。**任何小于 2pp 的差异，先用 3 个 seed 确认**。这一步成本低但决定你会不会追一个不存在的效应。

### 3.5 切片放大（免训练验证分辨率假说）

这是验证层里最有价值的一项：**用你现有的权重就能验证"分辨率是不是瓶颈"**，不需要任何训练。做法是让切片比模型输入小、再放大到模型输入（切 320 → 放到 640 即 2× 放大；切 213 → 3×）。当前代码把切片尺寸硬编码为模型 `image_size` 且不做上采样，所以需要改推理路径。

改造面（已核实，全部在 `tool_lib/`，不需要动 `src/`）：

- 核心一处：`det_infer.py` 的 `predict_for_infer()`，全流程唯一的前向入口，只有两个调用点；
- 放大是顺带的：`model.predict` 接受 PIL 图并自动 resize 到 `image_size`；
- 合并直接 import 上游的 `combine_predictions_tiles_and_global`，除放大倍数外合并语义与现有 SAHI 完全一致，是干净的单变量对照；
- 管道四处：命令行参数、`common.py` 默认值、`launcher.py` 配置键、多卡 shard 子命令透传；
- **`_det_fingerprint_options` 必须同步**——它决定复用指纹，漏了的话改了参数却复用旧结果，会得出"改了没变化"的假结论。

**判据**：切 320 放大到 640 后，`<8px` 档与 `8–16px` 档的召回是否明显上升。上升 → 分辨率是瓶颈，直接进第 4.1 节；基本不动 → 瓶颈不在分辨率，第 4 节的训练投入需要重新评估。

## 4. 训练方法层

### 4.1 分辨率（最大杠杆，但有一个必须避开的陷阱）

**陷阱**：训练时的实际分辨率来自 `transforms.py` 里硬编码的 `scale_jitter.sizes` 列表（13 个尺寸，**均值恰好是 640.0**，61.5% 的采样 ≤640）。`image_size` 只影响模型构造、decoder 的 anchor 缓冲和推理 resize。**所以把 `IMAGE_SIZE` 改成 800 只会改变评测分辨率，训练输入仍以 ≤640 为主，实验会得出"提高分辨率没用"的错误结论。**

正确做法：同时通过 `transform_args={"scale_jitter": {"sizes": [...]}}` 传入以目标分辨率为中心的尺寸列表（800 档用 640–1024，1024 档用 800–1280），并按同样节奏提高 `image_size`。

- 成本：显存/算力约 4×（640→1280），8GB 卡上 batch 需从 32 降到约 8 并配合梯度累积。
- 预期量级：人脸检测 640→1024 在 WIDER hard 上约 **+10 AP**（SCRFD 论文表格）；通用小目标 640→1280 约 +8 AP。这些是别的条件下的数字，只用于排序优先级。
- 判据：可达子集（≥16 设备像素）的 AP50 是否随分辨率单调上升。

### 4.2 采样策略（低成本，方向上确定正确）

当前按图均匀采样，而**损失是按 batch 内框总数归一化的**（`rtdetrv2_criterion.py:197-204`），所以每张脸的梯度权重是一样的——密集图不会被稀释。问题在**样本被抽到的频率**：combined 让每图采样的 `<8px` 框期望从 4.91 降到 3.53（−28%），密集图（>100 脸）采样概率从 1.82% 降到 1.13%（−38%）。

做法（不需要改上游采样器）：在数据准备阶段，把"GT>100"和"含大量 <8px 框"的原图在 train 列表里复制若干份。验收标准：把每图采样的 `<8px` 框期望恢复到 ≥4.91、密集图采样概率恢复到 ≥1.82%。

### 4.3 增强组合

- **重新打开 RandomZoomOut**：它是唯一会把脸变小的增强（只做 padding、把画布放大 1–4 倍，随后 ScaleJitter 缩到 480–800，目标在最终输入里变小；默认 `prob=0.5`）。但不要照抄默认的 `side_range=(1.0,4.0)`——那会把本就贴地板的脸再压到地板上。建议扫 `side_range=(1.0,2.0) × prob ∈ {0.3, 0.5}`。
- **RandomIoUCrop**（`prob=0.8`，裁剪 0.3–1.0 倍）会直接丢弃中心落在裁剪外的框，是另一个尺度与监督的扰动源，值得单独做开关对照。
- **Copy-Paste 的目标尺度**改为对齐 test 分布，而不是固定 12–28px；或者首轮整支关掉，把变量数降到最低。

### 4.4 标签分配与损失

现状：匹配代价是归一化坐标的 L1 + GIoU + focal 分类，**没有任何尺度感知项**（`matcher.py:102-129`）。对 6px 的框，归一化 L1 天然趋近 0、IoU 对 1px 偏移极度敏感，匹配几乎由分类代价主导。可考虑：NWD（把框建模为高斯，论文报告微小目标上 +6.7 AP）与 scale-aware loss 权重。注意 RFLA 的作者明确说它不适合多尺度混合场景，NWD 更稳妥。

### 4.5 结构

- **把被丢弃的 1/4 特征接回去**：`dinov3_vit_wrapper.py:53-117` 的 STA 分支已经算出 stride-4 特征，然后 `return c2, c3, c4` 把它扔了；现在检测头最小的先验框是 32px（`grid_size=0.05 × 640`），接入 1/4 层并配一个 16px 级先验，是针对"最小可检尺度"最直接的改动。
- **提高 query 数**（300 → 900）或做密度自适应（DQ-DETR 思路）：这是唯一能解开那 39.8% 密集 GT 的改动。
- **解冻 backbone**：可能是最大收益，也是最大成本；DINOv3 官方动机之一正是解决密集特征退化。放在分辨率和采样之后。
- **LR 单变量**：冻结主干下头部 lr 只有 5e-5×√2 ≈ 7.07e-5。曲线已进平台期说明"步数不够"不成立，但"步长太小"没有被排除，这是最便宜的待测项之一。

## 5. 数据层

按优先级排列：

1. **重建官方 val 评测集**（P0，见 1.3）：按 `wider_val_` 前缀重组 3,222 张，从 train 里剔除，下载官方 `ground_truth/` 包，跑官方三档 AP。
2. **按连拍序列重切本地划分**（P0）：保证同一序列不跨 split。
3. **修切片边界规则**（P2，必修）：`datasets/convert_datasets/convert_tools/face_wider_prepare.py:408` 的 `<50% 面积就丢框` 规则，对"保留面积 ≥25% 且可见区域 ≥8 设备像素"的 1,241 个重点候选**重新选窗口**，而不是删标签或提高阈值。生成独立 v2，v1 留作对照，按仓库约定 `--dry-run` → staging 校验 → 发布。
4. **密集/极小脸过采样清单**（P2，见 4.2）。
5. **切片比例与 Copy-Paste 尺度**（P3）：首轮 tile 占 10–15%（约 2,300 张）、不加 Copy-Paste；比例作为扫描变量而不是拍定值。

注意第 3 项的收益上限：切片边界影响 2,405 张 tile（占 combined train 的 11.57%），修好能恢复正确监督，但改变不了"72% 的 GT 小于一个 token"这件事。

## 6. 时间线

**今天（零训练成本）**
1. 把两个现有权重（原模型、combined）按 3.1 的方式各跑一遍，得到分档表。这一步直接告诉你 0.94pp 的差距落在哪个尺寸档。
2. 顺带跑一次 `maxDets=300` 的诊断。

**本周（零/低训练成本）**
3. 重组官方 val 评测集，跑官方三档 AP，建立对外锚点。
4. 切片放大改造（3.5）+ 现有权重复测，验证分辨率假说。
5. 修 `scale_jitter.sizes` 的覆盖参数（4.1 的前置）。

**下一步（开始花训练预算）**
6. 20,000 step 的分辨率阶梯：640 / 800 / 1024（用原图数据，隔离数据变量）。
7. 修切片边界生成 v2 + 密集图过采样。
8. 用胜出分辨率做数据消融：原图 / v2 / v2+ZoomOut / 原图+ZoomOut。
9. 结构改动（1/4 特征层、query 数）。
10. 多 seed 复验 + 完整 80,000 step。

## 7. 不要做的事

- **不要在当前口径下继续调切片比例和 Copy-Paste 尺度**：72% 的 GT 贴分辨率地板，信噪比不够，会得到随机结论。
- **不要只改 `IMAGE_SIZE` 就下"提高分辨率没用"的结论**（4.1 的陷阱）。
- **不要在 SAHI 阈值 0.3 下把 mAP 和全图路径的 mAP 直接比**（3.3 的口径警告）。
- **不要指望延长训练**（80,000 step 已进平台期）。
- **不要把本地 mAP/AP50 当对外指标**：它既不是官方 val 也不是官方 test，且 test 与 train 共享连拍场景。
- **不要用单 seed 结论支撑小于 2pp 的差异**。
